# 构建：人物

用于处理 `wiki/07 人物与城市/人物/` 和 `wiki/05 人物关系图谱/` 下的人物、关系功能、别名和关系管理页面。

这是人物模板的唯一负责人。城市、组织、项目和地点只路由到
`knowledge-engine/skills/build/life-experience/SKILL.md`，不要在本文件复制它们的模板。

这个 skill 必须由证据检索驱动。不要一次性把完整日记库或大量人物页塞进上下文。

## 先读

- `knowledge-engine/skills/common/quality-gate/SKILL.md`
- `wiki/08 来源索引/人物别名合并索引.md`
- `knowledge-engine/skills/build/people/scripts/collect_person_evidence.py`

只有高影响人物的关系演化、稳定认知或关系功能确需解释时，才读取 `knowledge-engine/skills/common/reasoning-lenses/SKILL.md`；身份、别名和互动事实保持中性。

## 契约

1. 创建或更新人物页前，先解析别名。
2. 对目标人物或批量对象运行证据收集器。
3. 只读取该人物的标准输出证据结果和目标页面。
4. 使用下方已知人物模板，从返回证据中综合页面。
5. 当人物功能发生变化时，更新关系功能页：支持者、镜子、组织信号源、反面样本、旧伤触发者、长期关系支点，或其他有证据的功能。
6. 对高频人物，按阶段/主题归并证据，正文保留代表性片段，其余通过 `source` 追溯。

## 证据检索流程

写或重写人物页前，先使用收集器。收集器是搜索工具：它把原始笔记证据打印到标准输出，供模型综合。不要把它当作最终人物页作者。

单个既有人物页：

```bash
python3 knowledge-engine/skills/build/people/scripts/collect_person_evidence.py \
  --page "wiki/07 人物与城市/人物/认识的人/工作/赵晓明.md" \
  --format json
```

姓名加别名：

```bash
python3 knowledge-engine/skills/build/people/scripts/collect_person_evidence.py \
  --person "赵晓明" \
  --aliases "晓明,xm" \
  --format json
```

所有已知人物页批量摘要：

```bash
python3 knowledge-engine/skills/build/people/scripts/collect_person_evidence.py \
  --all \
  --format summary
```

脚本不写文件。它只向标准输出打印单个人物的结构化 JSON，或批量摘要。常规人物构建不应创建 `原始知识库/临时人物证据/` 或其他临时证据目录。

## 综合流程

每次只处理一个标准输出证据结果：

1. 为目标人物运行收集器，并读取标准输出证据。
2. JSON 中的 `evidence`、`sources` 和 `category_counts` 只能作为综合输入；分类计数绝不是最终正文。
3. 读取既有人物页，保留别名、前置元数据和有价值的既有综合。
4. 只填写证据支持的字段。
5. 将所有原始笔记来源路径放进前置元数据的 `source`；正文保持精炼。
6. 在 `关键证据` 或 `关键事件` 中使用代表性片段；不要列出每一次命中。
7. 只有证据支持可执行提醒时，才写 `相处原则`。
8. 证据弱时，写短页；不要发明关系背景、性格、动机或互动偏好。

## 人物视角使用强度

- 种子人物和标准人物的身份、别名、关键事件先使用强度 0。
- 高影响人物的关系演化、稳定认知和相处原则最多使用强度 1；只有用户明确授权深度重解释时才使用强度 2。
- 运行 `python3 knowledge-engine/skills/common/reasoning-lenses/scripts/list_lenses.py` 动态发现人物；不在本 Skill 维护固定名单。
- 视角只能检查是否遗漏信任、共同实践、情感、长期承担或证据边界，不能从公共人物推断真实人物的动机和人格。
- 默认不在人物页写所用公共人物姓名；领域语言仍然是关系语言。

## 分层人物模板

人物页必须描述真实关系事实。绝不能把分类计数当作关系内容。类似 `沟通反馈 37 条；业务协作 25 条` 的句子只是内部诊断，不能出现在最终页面。

人物页按证据强度和关系影响分层。默认使用能回答真实问题的最短层级，不要把每个人都写成传记。

### 种子人物

用于别名消歧、用户提供的身份提示，或没有可用原始笔记证据的人物。

必需结构：

1. `## 核心定位`：一句话说明已知角色和证据边界。
2. `## 已知信息`：关系领域、别名和证据状态。
3. `## 关联`：只链接具体索引、来源页或相关实体。

不要添加共同经历表、稳定认知、关系价值、关键评价、互动建议，或泛泛的“重要人物”语言。

### 标准人物

用于至少有一条可用证据，但没有高影响关系权重的人物。

必需结构：

1. `## 核心判断`：一句话说明此人在用户生活系统中的功能，必须基于实际证据。
2. `## 关键证据`：1-6 条代表性条目。每条要概括发生了什么，以及它改变或揭示了什么。
3. `## 关系功能`：支持者、镜子、组织信号源、反面样本、旧伤触发者、长期关系支点，或温和的领域特定功能。推断必须标明。
4. `## 关联`：相关人物、城市、组织、事件、文档和原始来源。

### 高影响人物

用于配偶、子女、父母、长期亲密朋友、管理者、反复协作者，以及任何证据会改变重大判断的高频人物。

必需结构：

1. `## 核心判断`
2. `## 关系演化`
3. `## 关键事件`
4. `## 稳定认知`
5. `## 相处原则`
6. `## 关联`

高影响页应覆盖通过规范名和别名搜索到的主要人生阶段出现。使用代表性片段，不要列出所有提及。表格只有在明显改善扫描时才使用；条目列表也可以。

`关键评价` 不再是默认章节。只有证据支持可执行提醒时才写 `相处原则`，否则省略。

## 证据解释规则

- 把 `evidence_count` 和 `category_counts` 当作路由信号，不当作最终结论。
- 前置元数据、`相关日记`、生成索引或 `关联` 里的来源提及，不是关系证据；收集器会剥离这些区块。
- 通用别名可能产生误召回。如果返回证据看起来有噪声，减少别名后重跑，或先修复别名索引。
- 同一条证据应只有一个主要用途：关系时间线、稳定认知、关系价值或互动提醒。
- 高频人物按阶段/主题归并，正文选择 6-12 条代表性片段；完整可追溯性放在前置元数据，必要时保留收集器的标准输出 JSON。
- 低频人物保持判断克制、具体。

## 质量规则

- 不要在多个章节重复同一句日记证据。
- 不要生成占位字段或泛泛的 `待补充` 任务。
- 按关系领域解释证据。工作页可以讨论组织和责任链；家庭、室友、同学和朋友应使用关系语言。
- `相处原则` 是可执行综合，不是证据堆砌。
- 不要只说“出现在日记里”；要说清关系功能或证据类别实际改变了什么。
- 不要用分类计数写关系发展总结。
