设计探讨 · 非最终方案

导入账单后，记忆要怎么被「问出来」？

现在的做法是把账单解析成若干条线索，再由 Agent 逐条追问、一次只问一个开放式问题，靠对话慢慢把「消费旅程」聊成「已确认的记忆」。这份设计稿先拆解现状，再给出几种可以替代或叠加的构建方式，供讨论取舍——不涉及代码改动。

现状回顾

payment-statement.ts · Sources.tsx

账单导入后固定走三步：解析成候选线索 → 对话完善（可反复）→ 用户确认后构建入 Wiki。第二步是当前讨论的核心——完全由一问一答推进。

账单解析

按重复商户、地点、单日多事件、跨日期主题、旅程五种模式聚类，每条线索都带一个候选问题，按分数排序，最多保留 10 条。

对话如何展开（一次只问一件事）

五月中有段时间你在杭州密集出行，交通、住宿和几顿饭串在一起。想从哪个画面开始讲——是出发那天，还是到了之后印象最深的一件事？
是去看一个朋友的新工作室，顺便逛了西湖……
听起来这次更像是一次「探望 + 顺路玩」的旅程。那次见面之后，你和这位朋友的联系变多了吗？
下一条线索（代码人生咖啡）要等这条旅程聊得差不多，或用户主动切换才会被提起——目前没有「先快速处理简单线索」的路径。
问题一 · 输入成本

10 条线索若都走「开放问题 + 长文回答」，即便只挑最像故事的几条，单条也常常要 3～5 轮才能收敛，用户要一直打字。

问题二 · 顺序固定

Agent 按分数挑线索开场，用户没有「先说我最想聊的那条」的入口，也没法一眼看到全部线索再挑选。

问题三 · 无分级处理

琐碎、显而易见的线索（比如「就是每天买咖啡」）和真正有故事的线索走的是同一套重问答流程，没有「直接确认，不用细说」的轻量出口。

可以考虑的方向

4 种思路 · 可组合

下面四种方式都保留「对话仍是讲述记忆的核心手段、账单只提供线索」的原则，区别在于：用户何时看到全部线索、每条线索默认要花多少力气、以及深聊什么时候才被触发。

方向 A

线索地图先浏览，再选一条深聊

进入对话完善前，先给用户看一屏「线索地图」（时间线 + 分类气泡），用户自己挑感兴趣的一条开始，而不是系统按分数强制排序开场。

时间线总览 → 用户选一条 → 开放问答（同现状）
优势
  • 用户掌控从哪聊起
  • 改动小，只加一层选择
取舍
  • 没解决「琐碎线索也要重问答」
  • 仍然是逐条单线程
方向 B

先给旅程初稿，用户批注而非从零回答

Agent 先根据聚类直接写一段「推测性旅程叙述」草稿，明确标出哪些是推断、哪些是账单事实；用户用「这段对/这段错/帮我补充」的方式批注，而不是从空白问题开始回答。

推测草稿 → 用户批注/纠正 → 仅对分歧处追问
优势
  • 大幅降低打字量
  • 对的部分秒确认
取舍
  • 草稿写错会带偏用户
  • 需要更强的措辞克制
方向 C · 推荐

线索卡片墙：确认 / 简答 / 深聊 三档分级

所有候选线索同屏铺开成卡片，每条卡片默认给三个动作：「确认为事实」（跳过对话，直接收录客观信息）、「简单说说」（一次性小问答，不追问）、「展开细聊」（保留现状的深度追问）。用户按线索价值自己分级处理。

卡片墙全览 → 确认 简答 深聊
优势
  • 琐碎线索几秒处理完
  • 深聊只留给真正有故事的线索
  • 与现状对话体验兼容，可平滑升级
取舍
  • 要设计「确认」的可撤销与证据留存
  • 卡片墙本身多一屏信息密度
方向 D

自由写作模式，账单只做「提词」

跳过一问一答，直接给用户一个大文本框和线索侧栏做提示，让用户像写一段回忆随笔一样一次性写完整段旅程；Agent 事后再逐句核对、只对模糊处追问。

线索提示侧栏 → 用户一次性写完 → 事后核对少量追问
优势
  • 擅长写作的用户效率最高
  • 叙述连贯性天然更好
取舍
  • 不擅长表达的用户会卡在空白输入框
  • 与「先问一个具体问题」的产品原则冲突

推荐方案细节：线索卡片墙

方向 C 展开

对话完善这一步改成两层：先看全部线索卡片墙，按「确认 / 简答 / 深聊」分流；只有点了「展开细聊」的卡片才进入现状那套开放式追问对话，其余动作当场完成、不打开对话框。

建议的落地顺序

  1. 先做卡片墙全览。把已有的分数排序候选线索改成一屏可见的卡片列表，替代「Agent 挑一条直接开场」——这一步不涉及对话逻辑，风险最低。
  2. 加「确认为事实」和「简单说说」两个轻量动作。「确认」直接把线索的客观摘要（时间、地点、类别）写入记录草稿，不生成叙述性文字；「简单说说」用一次性预置选项 + 可选补充文字，不触发多轮追问。
  3. 「展开细聊」完全复用现状的开放式问答实现。不需要重写对话逻辑，只是把入口从「自动开场」改成「用户主动点击某张卡片」。
  4. 构建入 Wiki 前维持现有的确认态提示。「确认」和「简单说说」产生的内容依然只是草稿，和深聊产生的叙述享同一套 ready-to-build / 构建流程，不单独开一条通道。
