# 个性化指南

建议先让样例完整通过检查，再逐步替换内容和规则。一次改动太多分类，会让你无法判断哪个调整真正有效。

## 第一步：替换原始示例

删除 `原始知识库/日记/` 中的两篇虚构日记，放入你自己的 Markdown 文件。文件名最好包含可排序日期，例如：

```text
原始知识库/日记/2026-08-22 周末复盘.md
```

如果你的目录按年份拆分，请同步修改 `skills/build/people/scripts/collect_person_evidence.py` 的默认来源目录。

## 第二步：保留框架，清空示例判断

`wiki/` 中的内容全部是虚构样例。你可以保留各目录的总览和空结构，也可以删除具体页面后让第一次摄取重新生成。不要把示例判断当成你的个人结论。

## 第三步：调整分类

根 `AGENTS.md` 是唯一入口。新增类别时需要同时检查：

1. 是否真的需要一个新页面对象，而不是现有类别的子主题？
2. 哪个 Skill 是唯一负责人？
3. `impact-matrix.md` 是否需要新增一行？
4. `module-map.md` 和触发用例是否同步更新？
5. 验证器是否能发现路由遗漏？

完成后运行 `python3 tools/validate_skill_system.py`。

## 第四步：配置推理视角

人物视角文件位于 `skills/common/reasoning-lenses/references/figures/`。你可以删除不需要的视角，也可以按现有 frontmatter 和章节协议新增一个。下游 Skill 通过脚本动态发现，不需要维护人物名单。

视角文件应描述可核实的推理原则、适用问题和边界，不要收集未经证实的名言，也不要模仿口头禅。

## 第五步：调整标签

`tools/update_obsidian_tags.py` 只管理 `来源/`、`类型/` 和 `领域/` 命名空间，其他手工标签会保留。你可以在脚本的 `managed_tags_for()` 中增加稳定、可解释的目录映射。

## 推荐的演进方式

- 先积累 10—20 篇来源，再判断是否需要新类别。
- 让真实查询暴露结构缺口，而不是预先设计完美分类。
- 对重复出现的问题修改 Skill，不要只修补一次生成结果。
- 定期删除没有证据、没有查询价值、只是看起来完整的页面。
