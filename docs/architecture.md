# 架构说明

TwhWiki 的核心不是目录数量，而是四条必须同时成立的约束：证据与判断分层、单一入口路由、领域职责唯一、修改后可验证。

## 1. 两层知识模型

### 证据层：`原始知识库/`

这里存放日记、读书笔记、历史材料、对话转写等一手资料。正文默认只读，因为后续所有判断都需要能回到它核对。

允许由 Wiki 管道追加的内容应保持轻量，例如 YAML 元数据、`## 相关日记` 与 `## 关联`。这些内容只负责索引，不重写来源本身。

### 综合层：`wiki/`

这里不是来源副本，而是跨时间、跨来源维护的判断。页面按“主要对象”组织：人生阶段是一种时间结构，事件是一种决策结构，人物是一种关系结构，现实系统是一种运行结构，不能用同一套通用总结模板处理。

```text
原始事实 ──引用──> 综合判断
    ^                 |
    └────可追溯───────┘
```

## 2. 单一入口与 Skill 路由

根 `AGENTS.md` 先判断请求是否包含写入授权，再路由到一个或多个规范 Skill。

- `skills/consume/`：只读查询与综合。
- `skills/build/`：获授权后的摄取和领域构建。
- `skills/common/`：质量门、推理视角、信号检测和 Skill 体系维护。

每个类别只有一个模板负责人。例如人物页只由 `build-people` 定义，`wiki-build` 只负责把人物更新任务分发过去，不复制人物模板。这样能避免同一页面在不同流程中出现互相冲突的规则。

## 3. 影响矩阵

一份新日记可能同时改变职业系统、关系证据、当下状态和一个长期循环。构建编排器必须逐行检查影响矩阵，而不是凭直觉只选一两页。

每行只能使用四种状态：

- `update`：有新证据，更新该层。
- `link-only`：判断没变，只补导航或来源链接。
- `no-op`：已经检查，没有影响。
- `defer`：可能有影响，但证据不足或需要更多材料。

`defer` 是一种诚实的完成状态，不应该被模型用猜测填满。

## 4. 领域模型

| 层 | 要回答的问题 |
|---|---|
| 个人主线 | 长期自我叙事和想要的人生方向怎样变化？ |
| 人生阶段 | 如何进入、经历并离开一个阶段？ |
| 事件与决策 | 当时有哪些选项、权衡、后果与事后判断？ |
| 反复循环 | 哪个触发—反应—代价—修正模式在重复？ |
| 人物关系 | 这个人的关系功能和相处边界怎样变化？ |
| 现实系统 | 职业、身体、家庭、资产、注意力等系统怎样运行？ |
| 思维模型 | 哪个判断机制能被真实经历验证或推翻？ |
| 状态追踪 | 哪项状态正在优化、劣化、稳定或证据不足？ |
| 近况对话 | 基于证据，有什么尚未被完整说出的理解？ |

目录 `10` 被有意留空：跨年份时间线已经归入 `02 人生阶段/`，避免维护两套平行时间结构。

## 5. 推理视角的边界

推理视角只影响“怎样解释”，不影响日期、原句、实体、金额和事件顺序。标准流程是：

1. 先建立不含人物观点的中性证据卡。
2. 根据问题选择一个主视角。
3. 让主视角决定关注点、推理路径和停止位置。
4. 必要时只加入一个有明确任务的辅助视角。
5. 把解释放回领域模板，并标清推断。

这避免了“先生成通用结论，再换一个名人语气包装”的伪多视角问题。

## 6. 完成定义

一次写入只有在以下条件满足后才算完成：

- 影响矩阵每一行都有结论。
- 重要判断存在来源或推断标记。
- 公共导航和日志在确有变化时已更新。
- 标签脚本第二次运行 `updated=0`。
- WikiLink 检查 `missing=0 ambiguous=0`。
- Skill 体系检查通过。
- 准备共享时隐私检查通过，并完成人工复核。

自动化检查证明的是结构约束，不证明人生解释一定正确。重要结论仍应由知识库主人复核。
